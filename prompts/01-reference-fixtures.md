# Prompt 1 — Generate reference test fixtures

Run this in a **fresh context, before any implementation exists.** See the note
at the bottom for why that ordering is not optional.

---

Read `AGENTS.md` first. Then generate the golden test fixtures for this
project's Japanese morphological analysis pipeline.

## Critical constraint: independence

These fixtures are the ground truth the pipeline will be measured against, so
they must be derived independently of any implementation.

- Do **not** install, import, or run fugashi, MeCab, SudachiPy, or any other
  morphological analyzer.
- Do **not** write any pipeline code, scaffolding, or project structure.
- Derive every expected value from your own knowledge of Japanese morphology.

If expectations are generated by running an analyzer, the test only proves the
analyzer agrees with itself. That is worthless as a correctness check, and it
would silently bless whatever alignment bugs the analyzer has.

## What to produce

15–20 fixture entries in `backend/tests/fixtures/tokenization.json`.

The format is specified in `AGENTS.md` under "Fixture format". Follow it
exactly — in particular, furigana uses **spans**, never per-character readings.

Include at least one entry for each of:

- a verb with trailing okurigana (reading must cover only the kanji)
- **a compound verb with interspersed okurigana** — 申し込む, 受け取る, 引っ越す,
  or similar, where kana sits *between* kanji. This is the case that separates
  a correct implementation from naive suffix-stripping, so do not skip it or
  substitute another trailing-okurigana verb.
- a multi-kanji compound
- a jukujikun compound, whose reading cannot be split per character
- the same character read with on'yomi in one entry and kun'yomi in another
- a conjugated form whose lemma differs from its surface form
- a line mixing kanji, hiragana, and katakana
- a particle-heavy sentence
- both a な-adjective and an い-adjective
- a sentence containing a number with a counter

Readings in fixtures are written in **hiragana**, not katakana.

`pos` values must come from the closed English vocabulary listed in `AGENTS.md`
under "Part-of-speech values" — `noun`, `verb`, `particle`, `adjective-i` and
so on. Do **not** use UniDic's Japanese tags (名詞, 動詞). The pipeline will map
its output into this vocabulary later; the fixtures define the target.

Do **not** include JMdict glosses or English translations. Fixtures cover
tokenization, lemmas, readings, and furigana alignment only — stable linguistic
facts. Glosses would couple these tests to a specific dictionary release.

## Writing the sentences

Write them yourself. Ordinary everyday sentences, at roughly beginner-to-
intermediate textbook level.

Do **not** use song lyrics, or text copied from any published source. This repo
must never contain licensed text, and git history is permanent.

Keep them short — one clause or two. Long sentences make failures harder to
localize without testing anything additional.

## Flag your uncertainty

Add a `"confidence"` field to every entry, either `"high"` or `"needs-review"`.

Mark `needs-review` wherever a reading is genuinely context-dependent,
involves a proper noun, or has more than one defensible tokenization. Do not
mark everything high to look confident — an unflagged wrong fixture is worse
than a flagged uncertain one, because it becomes a permanently enshrined bug.

Then write `backend/tests/fixtures/REVIEW.md` listing every `needs-review`
entry with one line explaining the specific uncertainty, so a human can verify
exactly those cases rather than re-checking all twenty.

## Output

Exactly two files:

- `backend/tests/fixtures/tokenization.json`
- `backend/tests/fixtures/REVIEW.md`

Nothing else. No project scaffolding, no dependencies, no test runner.

---

## Why this runs first, in its own context

An agent that has just written the tokenizer will write fixtures that agree
with the tokenizer, because its own implementation is the most available
reference in context. That is true even when it is told not to run the code.

Authoring the fixtures before any implementation exists removes the
possibility. The expectations come from knowledge of Japanese rather than from
observed program output, which is the only thing that makes them a real check.
